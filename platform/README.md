# Sportive Hub platform

The backend, admin dashboard and patient portal for Sportive Hub. One Next.js app that serves:

| Area | URL | Who |
|---|---|---|
| Admin dashboard | `/admin` | Staff: overview, sessions, updates, patients |
| Patient portal | `/portal` | Patients: profile, sessions, points, referral code |
| JSON API | `/api/...` | The two UIs above, and later a mobile app or the public website |

It is separate from the public website in `../public_html/`, which stays a plain static site.

## Stack

- **Next.js 16** (App Router, TypeScript): pages, API route handlers and the request guard (`src/proxy.ts`) in one deployable.
- **Prisma 7** with **MySQL/MariaDB**: Hostinger's hosting plans include MySQL, so no extra database service is needed.
- **Auth:** email + password (bcrypt), sessions as signed JWTs in an HttpOnly cookie (`jose`).
- **Validation:** `zod` on every request body and query string.
- **UI:** Tailwind CSS 4 with the brand palette from the website (olive, sand, milk, pastel, charcoal).

Why this shape: Hostinger runs Node.js apps with `app_type: next` on Node 22, the same way the other sites on the account run, and attaches a MySQL database by writing `DATABASE_URL` into the app's environment. A single app means one deploy, one database and one place for business rules.

## Folder map

```
prisma/
  schema.prisma          the data model (User, Session, Update, LoyaltyTransaction)
  migrations/            SQL migrations, generated by `prisma migrate dev`, applied with `migrate deploy`
  seed.ts                first admin account (+ demo data with SEED_DEMO=1)
prisma7.config.ts        Prisma CLI config (reads DATABASE_URL from .env)
src/
  proxy.ts               runs before matched requests: CSRF check, login redirects, role gate
  app/
    api/                 route handlers (see API below)
    admin/               staff pages (layout with sidebar, overview, sessions, updates, patients)
    portal/              patient pages
    login/ register/     auth pages
  lib/
    auth/                password hashing, token signing, cookie session helpers
    services/            business logic: auth, sessions, updates, patients, overview, portal
    loyalty.ts           points rules: amounts, tiers, rewards, recordPoints, applyReferral
    referral.ts          SPORT-XXXXXX code generation and links
    validation.ts        zod schemas for every input
    http.ts              route() wrapper, HttpError, JSON helpers
    db.ts                the Prisma client
  components/            React components (ui primitives, forms, sidebar)
  generated/prisma/      Prisma client, generated, not committed
```

Pages read the database through `lib/services` directly (Server Components). Forms call the JSON API. Both go through the same service functions, so rules live in one place.

## Run it locally

Needs Node 22 and a MySQL or MariaDB server.

```bash
cd platform
npm install
cp .env.example .env            # then edit DATABASE_URL, AUTH_SECRET, ADMIN_*
```

Create the database and user once (adjust names to match your `.env`):

```sql
CREATE DATABASE sportive_hub CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'sportive'@'localhost' IDENTIFIED BY 'sportive-dev-pass';
GRANT ALL PRIVILEGES ON *.* TO 'sportive'@'localhost';   -- `migrate dev` needs to create a temporary shadow database
```

Then:

```bash
npx prisma migrate dev          # applies migrations, regenerates the client
npx prisma db seed              # creates the admin from ADMIN_EMAIL/ADMIN_PASSWORD (+ demo data if SEED_DEMO=1)
npm run dev                     # http://localhost:3000
```

Demo accounts when `SEED_DEMO=1`: `mariam@example.com`, `omar@example.com`, `nour@example.com`, password `Patient-Demo-2026`.

Other scripts: `npm run build` (production build, also type-checks every route), `npm run lint`, `npx prisma studio` (browse the data).

### Changing the data model

1. Edit `prisma/schema.prisma`.
2. `npx prisma migrate dev --name describe_the_change` creates `prisma/migrations/<timestamp>_describe_the_change/` and applies it locally.
3. Commit the migration folder with your code. On the server, `npx prisma migrate deploy` applies pending migrations without needing a shadow database.

## Data model

- **User**: both roles in one table (`role` = `ADMIN` | `PATIENT`). Patients get a unique `referralCode` and may have `referredById`. `loyaltyPoints` is the spendable balance, `lifetimePoints` what was ever earned (drives the tier). `passwordHash` never leaves the server.
- **Session**: an appointment for one patient: `type` (physio, EMS, IV, …), `branch`, `startsAt`, `durationMinutes`, `practitioner`, `status`, `notes`, `isComplimentary`, and `pointsAwardedAt` (set once attendance points were paid).
- **Update**: announcement, platform update or health tip; `publishedAt` null = draft.
- **LoyaltyTransaction**: append-only audit row for every points change, with `reason`, optional `note`, `referenceId` (session or referred user) and `actorId` (the admin, for manual changes).

## Loyalty rules

All numbers live in `src/lib/loyalty.ts`.

| Event | Points | Reason code |
|---|---|---|
| A new patient signs up with your code | +50 to you | `REFERRAL_BONUS` |
| You sign up with someone's code | +25 to you | `WELCOME_BONUS` |
| A session of yours is marked completed | +10 (once per session) | `SESSION_ATTENDED` |
| Staff add or deduct by hand (note required) | any | `MANUAL_ADJUSTMENT` |
| Redeem "One free session" | −100 | `REWARD_REDEMPTION` |

Tiers by lifetime points: Bronze (0), Silver (300), Gold (800). Spending points never lowers a tier.

Every change goes through `recordPoints()` inside a database transaction: the balance is updated with an atomic increment and the audit row is written in the same transaction, so the two can never disagree, and a deduction below zero rolls back with a 409. Referral bonuses are paid at sign-up (as specified); if fake sign-ups become a problem, move the `applyReferral` call from registration to the first completed session.

## API

All responses are JSON. Errors look like `{ "error": "message", "details": [{ "path": "field", "message": "..." }] }` with the matching status (400 bad JSON, 401 not signed in, 403 forbidden, 404, 409 conflict, 422 validation).

Public:

| Method | Path | Body / query | Notes |
|---|---|---|---|
| POST | `/api/auth/register` | `fullName, email, password, phone?, referralCode?` | Creates a patient, pays bonuses, sets the cookie |
| POST | `/api/auth/login` | `email, password` | Sets the cookie; also returns `token` for `Authorization: Bearer` clients |
| POST | `/api/auth/logout` | | Clears the cookie |
| GET | `/api/updates` | `page, perPage` | Published updates only. Usable from the public website |

Signed in (any role):

| GET | `/api/me` | | Profile, tier, referral link, rewards, upcoming sessions, points history, latest updates |
|---|---|---|---|

Admin only:

| Method | Path | Body / query |
|---|---|---|
| GET | `/api/admin/overview` | |
| GET | `/api/admin/sessions` | `status, patientId, upcoming=1, page, perPage` |
| POST | `/api/admin/sessions` | `patientId, type, startsAt, branch?, title?, durationMinutes?, practitioner?, notes?, isComplimentary?` |
| GET / PUT / DELETE | `/api/admin/sessions/:id` | PUT takes any subset plus `status`; `COMPLETED` awards points once |
| GET | `/api/admin/updates` | `page, perPage` (includes drafts) |
| POST | `/api/admin/updates` | `title, body, kind?, publish?` |
| PUT / DELETE | `/api/admin/updates/:id` | `publish: true/false` publishes or unpublishes |
| GET | `/api/admin/patients` | `q, page, perPage` (name, email, phone or exact code) |
| GET / PATCH | `/api/admin/patients/:id` | PATCH: `fullName?, phone?, isActive?` |
| POST | `/api/admin/patients/:id/points` | `points` (non-zero, negative to deduct), `note` |
| POST | `/api/admin/patients/:id/redeem` | `reward: "FREE_SESSION"` |

## Security

- **Passwords:** bcrypt, cost 12, never returned. Login compares against a dummy hash when the email is unknown, so timing does not reveal which emails exist, and the error message is the same either way.
- **Sessions:** HS256 JWT (`sub`, `role`, `name`, 7-day expiry) signed with `AUTH_SECRET` (32+ random chars; rotating it signs everyone out). Stored in an `HttpOnly`, `Secure` (in production), `SameSite=Lax` cookie, so scripts cannot read it and cross-site forms do not carry it.
- **Two gates:** `src/proxy.ts` verifies the token before `/admin`, `/portal`, `/api/admin` and `/api/me` (redirect or 401/403), without touching the database. Then every page and route handler calls `getSessionUser()` / `requireAdmin()`, which re-reads the user, so a deactivated account or a changed role takes effect on the next request even though the token is still valid.
- **CSRF:** state-changing `/api` requests that carry the cookie must come from the same site (`Sec-Fetch-Site`, or `Origin` matching the host); otherwise 403. Bearer-token requests are exempt because browsers never send those automatically.
- **Input:** every body and query string is validated with zod before it reaches a service; unknown fields are dropped, and the API never echoes stack traces (unexpected errors log server-side and return a generic 500).
- **Secrets** live in environment variables only. `.env` is git-ignored; `.env.example` has placeholders.
- **Headers:** `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and a referrer policy are set in `next.config.ts`. The app tells search engines not to index it.

Not done yet, and worth doing before opening the portal to the public: rate limiting on `/api/auth/*` (e.g. `rate-limiter-flexible` backed by MySQL), email verification, password reset, and automated tests in the repo (the API and browser checks used so far live outside it).

## Deploy to Hostinger

The app runs as its own Hostinger website (for example `app.sportive-hub.com`), separate from the static site.

1. **Create the website** in hPanel (Websites → Add website → Node.js), on a subdomain such as `app.sportive-hub.com`. Business and Cloud plans run Node.js apps.
2. **Connect the repository**: Websites → Manage → Advanced → Git, then pick this repo and branch `main`, with **root directory** `platform` (this app lives in a subfolder). Build settings: app type Next.js, Node 22, build script `build`, output `.next`.
3. **Attach a database**: Node.js → Database. Hostinger creates it and writes `DATABASE_URL` (and `DB_*`) into the app's environment.
4. **Set the other variables** (Node.js → Environment variables): `AUTH_SECRET` (`openssl rand -base64 48`), `APP_URL=https://app.sportive-hub.com`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_NAME`, `NODE_ENV=production`. Leave `SEED_DEMO` unset.
5. **First deploy**: push to `main` (or Deploy in hPanel). After the build, run the migrations and the seed once. From a machine that can reach the database with the external host from hPanel:
   ```bash
   DATABASE_URL="mysql://USER:PASSWORD@srvNNNN.hstgr.io:3306/DBNAME" npx prisma migrate deploy
   DATABASE_URL="..." ADMIN_EMAIL=... ADMIN_PASSWORD=... npx prisma db seed
   ```
   Later deploys: run `npx prisma migrate deploy` again whenever a commit adds a migration.
6. Sign in at `https://app.sportive-hub.com/login` with the admin account.

The same can be done with the Hostinger API or the `hostinger` CLI (`hostinger up platform --domain app.sportive-hub.com --type nodejs --app-type next --node-version 22`).
